Five-Stage Pipelined RISC-V Processor

VerilogRISC-VModelSimDigital LogicComputer Architecture

Academic project / Rose-Hulman / CSSE 232: Computer Architecture / Team project

Following an instruction all the way through.

As part of a team, I worked on a RISC-V processor, progressing from a single-cycle design toward a five-stage pipeline. The challenge was keeping instructions moving while preserving the dependencies between them.

The datapath

Our implementation work covered instruction fetch (IF), decode (ID), execute (EX), memory (MEM), and write-back (WB), with IF/ID, ID/EX, EX/MEM, and MEM/WB pipeline registers carrying state between stages.

IF → IF/ID → ID → ID/EX → EX → EX/MEM → MEM → MEM/WB → WB

Dependencies and hazards

We worked on forwarding and hazard detection for data dependencies, load-use stalls, and control hazards from branches and jumps.

Why forwarding and stalls matter

A dependent instruction can need a result before it reaches write-back. Forwarding makes an available result usable sooner; a load-use dependency can still require a stall while the value arrives from memory. Branches and jumps also require care so instructions follow the correct control path.

Tests and verification

We developed and debugged Verilog testbenches using ModelSim waveforms, and validated processor behavior with instruction and program-level tests, including GCD and relative-prime programs.

Collaborative implementation. Work described here reflects our team's design and verification work; final pipeline completion status is still to be confirmed.

RHIT Schedule Builder

Academic project / CSSE 280: Web Programming / Ongoing team project

A clearer way to plan the next term.

The problem

Planning classes means finding courses and bringing those choices into a usable schedule. This full-stack application is intended to improve that experience for Rose-Hulman students.

The solution

A text editor.
A different foundation.

JavaAVL treesJUnit 5

Academic project / Editor Trees / CSSE 230: Data Structures & Algorithm Analysis

The document is a tree. Keeping it balanced is the challenge.

I built an AVL-tree-based text editor in Java that represents text as a balanced tree instead of a flat buffer. The project connects the theory of balanced trees to the mechanics of text operations.

For 50,000 characters inserted in sorted order, EditTree took 8 ms versus 4,865 ms for the naive binary search tree, roughly 600× faster in this benchmark. That result applies to this comparison; it isn’t a claim about every editing workload. A 13-test JUnit 5 suite backs the implementation.

Why use a balanced tree?

Sorted input can make an unbalanced search tree behave like a linked list. AVL rotations keep the tree’s height logarithmic, limiting the path through it as the document grows. The useful lesson here is how much the representation can change the cost of an operation.
